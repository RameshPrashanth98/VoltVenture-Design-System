01

Foundations

Foundations are the decisions that everything else inherits. They are not components and they are not opinions about screens — they are the finite sets a designer or engineer is allowed to pick from.

Brand principles, read from the work

Four things are consistently true across the boards, and each one has a direct consequence for how the system is built:

  • Black is the canvas, green is the verb. Electric green never appears as decoration. It marks the single active thing on screen — the primary action, the current tab, the live status, the number that matters. One green element per view is the working rule.
  • Contrast carries hierarchy, not weight. The marketing type shifts emphasis by switching colour (white → grey → green) inside a single sentence rather than by changing weight. In-product, the same job is done by the black/grey/mid-grey text ramp.
  • Everything is rounded, nothing is sharp. Pills, squircles, circles. There is no 0-radius surface anywhere in the product. This is the strongest single signal of the brand and radius tokens should never bottom out at zero.
  • Density is low, targets are large. Cards are generously padded, nav items are 56pt circles, rows are tall. The system is tuned for one-handed use in a moving vehicle, which sets the touch-target floor higher than the platform minimum.

02

Design tokens

Three tiers. A value only ever enters the codebase at tier 1, and a component only ever consumes tier 2 or 3. Skipping a tier is how design systems rot.

Tier architecture

TierNameExampleWho reads it
1Primitivecolor.green.500 = #C6FF2DNobody, directly. The raw palette.
2Semanticcolor.action.primary → green.500Designers and engineers, everywhere.
3Componentbutton.primary.bg → action.primaryOnly the component that owns it.

The rule that makes this worth doing: when the brand green shifts, you change one primitive. When you decide primary actions should be black instead of green, you change one semantic and every button, tab, and toggle follows.

Naming convention

[category].[concept].[variant].[state]

color.action.primary.default
color.action.primary.pressed
color.text.secondary
color.surface.raised
space.400
radius.card
font.size.heading.lg
elevation.raised
  • Lower camel, dot-separated. Transforms cleanly to colorActionPrimary (JS), color_action_primary (Dart/XML), --color-action-primary (CSS).
  • Numeric scales, not t-shirt sizes, for spacing. space.400 inserts new steps without renaming; space.md does not.
  • T-shirt sizes are fine for type and radius, where the set is stable and designers speak in those terms.
  • No token is named after its value. color.green is banned; color.action.primary is the name.

What is not a token

One-off values used exactly once, layout decisions specific to a single screen, and anything that would need a comment to explain. If it cannot be named without referring to the screen it appears on, it belongs in that screen's code, not in the system.

03

Styles

A style is a named bundle of tokens applied together. Tokens are the atoms; styles are the molecules a designer actually reaches for in Figma.

Style typeBundlesCountFigma equivalent
Colour stylesOne semantic colour token~24Colour style
Text stylesfamily + size + weight + line-height + tracking14Text style
Effect stylesshadow layers4Effect style
Grid stylescolumns + margin + gutter1Layout grid

Rules for styles

  • A style never contains a raw value. It composes tier-2 tokens only.
  • If a designer needs a combination that no style provides, that is a signal to add a style — not to detach and override.
  • Text styles carry line-height and tracking. Applying a text style should never require a follow-up adjustment.
  • Effect styles are the only sanctioned source of shadow. Hand-typed shadow values are a review failure.

Contrast — the one thing to get right

Electric green is a light colour. Its contrast against white is 1.36:1, which fails every threshold there is. Against Volt Black it is 15.4:1.

On white
Green text on white — 1.36:1, unusable
Green 700 on white — 4.6:1, passes AA
Black on green — 15.4:1
  • Green is a background colour, not a text colour, on light surfaces. Foreground on green is always #0F0F0F.
  • Green as text is permitted only on black or charcoal surfaces, where it clears AAA.
  • Where green text on white is unavoidable, use color.green.700.
  • #808080 on white is 3.9:1 — it passes AA for large text only. Secondary body copy below 18pt should use a darker step; add grey.600 #6B6B6B (4.8:1) if that case appears.
  • Never encode state in green alone. The live indicator pairs the dot with a text label in the mockups — keep that pairing.

05

Typography

Two families. Manjari carries the brand voice; Inter carries the interface. The split is by role, not by size.

Manjari
Display / brand
100 · 400 · 700

Headlines, hero statements, the wordmark, large numerals. Its rounded terminals are the typographic echo of the radius language.

Inter
Body / interface
400 · 500 · 600 · 700

Everything functional: labels, rows, buttons, captions, data. Tall x-height survives small sizes and glare.

The wordmark on the logo board is a customised, monoline redraw — not Manjari as shipped. Treat the wordmark as an asset, never as live text. Confirm with the brand owner whether a licensed custom cut exists before anyone tries to set the logo in a font.

Rules

  • Manjari above 24pt, Inter below. Manjari's low-contrast rounded forms lose legibility at interface sizes.
  • Negative tracking on large sizes only. −0.02em at 28pt and above, 0 at body sizes, positive tracking only on overline.
  • Tabular figures for all data. Fares, distances, points, times, counts. font-variant-numeric: tabular-nums — non-negotiable for anything that updates live during a ride.
  • Sentence case everywhere except overline. The mockups use uppercase only for small meta labels.
  • Dynamic Type support to at least the accessibility-medium step. All sizes above are the default step, not fixed values.
  • Line length in body copy caps around 60 characters, which at 15pt is comfortably inside the 361pt content width.

Elevation

VoltVenture expresses depth two different ways depending on the surface underneath. Both are defined; using the wrong one is the most common way this system will be broken.

Model A — shadow, on light surfaces

Soft, wide, low-opacity. Neutral black at low alpha, never coloured, never tight.

Model B — surface lightness, on dark surfaces

Shadow is invisible on #0F0F0F. On dark, depth is carried by stepping the surface lighter — the same technique the black stat card uses for its progress track.

Rules

  • Never stack more than two elevation levels in one view. The mockups keep it to one raised card plus one floating tab bar.
  • Elevation is not decoration. It signals that a surface is separable from what is behind it — draggable, dismissible, or persistent over scrolling content.
  • Android maps these to elevation dp values (2 / 6 / 12); iOS uses the shadow layers directly. Keep the semantic names identical across both.
  • No coloured shadows. A green glow under a green button is off-brand for a system whose stated principle is "no decoration, no noise".

08

Grid

A 4-column phone grid. Simple, because phone layouts are overwhelmingly single-column and the grid's real job is enforcing consistent margins.

393pt · 4 col · 16pt margin · 16pt gutter
PropertyValue
Columns4
Margin16pt
Gutter16pt
Content width @393pt361pt
Column width @393pt78.25pt
Baseline grid4pt

Behaviour

  • Margin is fixed, columns are fluid. On a 430pt device the margin stays 16pt and the columns grow. Content should never widen its margins on a larger phone.
  • Safe areas sit outside the grid. Top inset for the Dynamic Island, bottom inset for the home indicator — the tab bar floats above the bottom inset with space.500 clearance, as in the mockup.
  • Full-bleed exceptions: maps, hero imagery, and the top of scroll views may extend edge to edge. Everything else respects the margin.
  • Tablet is out of scope for v0.1. If it lands, the grid extends to 8 columns at 24pt margins rather than stretching the phone layout.

09

Iconography

Solid glyphs with rounded geometry, drawn on a 24pt grid. The icon language follows the radius language — no sharp corners, no thin hairlines.

Construction

PropertyValue
Canvas24 × 24pt
Live area20 × 20pt
Padding2pt all sides
Default styleSolid / filled
Stroke, where used2.2pt, round cap, round join
Corner radius on glyphs1–2pt minimum
Sizes16 / 20 / 24 / 32pt

Rules

  • Filled for navigation and status; stroked for directional affordances. Tab bar glyphs are solid; the row chevron is a stroked arrow. This is the pattern in the mockups and it usefully separates "where you are" from "where this goes".
  • Icons inherit text colour via currentColor. They are never given their own colour token.
  • Optical sizing over mathematical. A circle at 24pt reads smaller than a square at 24pt; adjust to match visual weight, not bounding box.
  • An icon never carries meaning alone in a primary flow. Tab bar items, status indicators, and destructive actions all pair with a label.
  • Icons render at 1× vector; no bitmap fallbacks, no multi-colour glyphs.

10

Border

Borders are used sparingly. The system separates surfaces with fill and space first; a border is the fallback when neither is available.

TokenWidthColourUse
border.width.none0—Default for filled surfaces
border.width.hairline1ptborder.subtleDividers, outlined chips, input rest state
border.width.strong1.5ptborder.strongInput focus, selected card
border.width.focus2ptaction.primaryKeyboard / switch-control focus ring, 2pt offset

Rules

  • Fill beats border. The settings rows in the mockup are separated by a #F5F5F5 fill and a gap, not by dividing lines. Follow that pattern first.
  • One divider style. 1pt #EBEBEB on light, 1pt #2F2F2F on dark. Inset dividers align to the content edge, not the screen edge.
  • Focus rings are green and always visible. Green on both light and dark surfaces gives adequate contrast against the focused element, and it is the one place where green outlines rather than fills.
  • Borders never replace elevation. A card is either raised with shadow or outlined with a hairline — never both.
  • Border colour is a semantic token. Never a raw grey step.

Radius

The most recognisable property in the system. Nothing in VoltVenture has a square corner — the scale starts at 8pt and there is no zero step.

xs · 8

TokenValueApplied to
radius.xs8ptBadges, small chips, progress tracks
radius.sm12ptInline tags, thumbnails, inputs
radius.md16ptList rows, secondary cards
radius.lg20ptStandard content card
radius.xl28ptFeature cards, the black stat block, map container
radius.2xl36ptBottom sheets, full-width hero surfaces
radius.full999ptButtons, pills, avatars, tab bar circles, status dots
radius.icon22.37% squircleApp icon only — iOS continuous corner mask

Rules

  • Nesting rule: inner radius = outer radius − padding. A 28pt card with 16pt padding holds 12pt children. Equal radii on nested surfaces read as a mistake.
  • Every interactive control is radius.full. Buttons, tabs, toggles, avatars. Nothing interactive uses a corner value from the middle of the scale.
  • Containers use the numeric scale, and larger surfaces take larger radii — radius scales with the element, it is not constant.
  • Use continuous curvature where the platform offers it. UIBezierPath continuous corners on iOS; the squircle is central to how the brand reads and standard circular corners will look subtly wrong next to the app icon.
  • There is no radius.none. If a square corner is needed, that is a design conversation, not a token lookup.

Open items before v1.0

  • Status colours are missing. There is no error, warning, or informational colour anywhere in the boards — only green for positive/live. A ride-hailing product needs at least a destructive red (cancel ride, payment failed). This needs a brand decision, not a system decision.
  • Motion tokens are not covered. Duration and easing belong in foundations; the boards include video I could not read. Worth extracting from the prototype.
  • Manjari licensing for the wordmark — confirm whether a custom cut exists, per §05.
  • Dark mode mapping. The semantic table has a dark column ready, but it has not been validated against real screens.
  • Grey 600 (#6B6B6B) may be needed for small secondary text on white, per the contrast note in §04.
  • Radius values are derived from mockup measurement, not from a spec board. They are internally consistent and match what is visible, but worth confirming against the source Figma file if you have access to it.
